# backend/ — FastAPI Trading Bot Backend

## Purpose

Core trading bot API and business logic. Serves the React frontend via REST and WebSocket. Manages all trading operations, market data, user auth, and the trading strategy engine.

## Local Contracts

- Routers mount under `/api` with no version segment: `/api/auth`, `/api/bot`, `/api/dashboard`, `/api/trades`, `/api/signals`, `/api/positions`, `/api/orders`, `/api/settings`, `/api/performance`. `/health` and `/` are mounted at root.
- Auth: one HS256 JWT (24h expiry) issued as the `fubot_token` cookie (`httpOnly`, `secure`, `samesite=lax`). No refresh tokens. Login is rate limited to 5 failed attempts per IP per 15 minutes. All authenticated endpoints accept the JWT via the httpOnly cookie *or* `Authorization: Bearer <token>` header (header fallback added for localStorage-durable token flow).

- API key/secret encrypted at rest using `backend/encryption.py`
- Binance Futures USDS-M only — no spot trading
- Database: PostgreSQL via SQLAlchemy 2.0 async
- All bot state changes logged to `equity_log` table
- Live order-flow failure logs include the signal id and failing stage; LIMIT response logs include the signal id, exchange order id, time-in-force, and status for lifecycle correlation. Never log signed URLs or credentials.
- Daily and weekly drawdown guards block new entries while the BotEngine loop remains available to observe reset windows; they do not stop the independently running PositionManager or flatten existing positions. Treat their configured R values as entry brakes, not guaranteed account-loss caps.
- `PositionManager` must initialize from persisted `bot_mode` before startup reconciliation; close accounting and live exchange cleanup must use the individual `Position.mode`, not a mutable manager-wide mode. Add positions opened during a scan to that scan's daily-loss position snapshot with `unrealizedPnl` and the frozen `initialRiskDistance`.
- Trading defaults come from `backend/config.py`: `RISK_PERCENT`, `MAX_POSITIONS`, `DAILY_LOSS_LIMIT_R` (-3R), `RR_MIN` (3.0), `CHECK_INTERVAL_SECONDS`, `LEVERAGE_BTC`, `LEVERAGE_ALTS`
- **The backtest harness measures net-of-fee expectancy over a paginated, single-window dataset** (2026-10-19): `backend/backtest.py` shipped with five defects that made its output unusable — a single-page fetch capped 5m at 1000 bars (3.47 days regardless of `--days`); **no fee modelling at all**, so expectancy was GROSS while panel cycle 1 concluded fee drag, not exit geometry, is the binding constraint; 1h/5m/15m fetched independently (spanning 41.7/3.5/10.4 days) then stitched **by index**, so the trend filter read a different month than its entries; entries filled at a 1h candle open while 3CANDLE signals come from 5m; and a fill model that ignored live's LIMIT-at-midpoint, signal expiry and R:R re-check at the fill. `backend/backtest_data.py` now owns fetching (paginated, interval-aware, all intervals pinned to one `[start, end)`, still-forming bars dropped, series joined on `open_time` — never by index), reached through the new `BinanceService.get_klines_window(symbol, interval, start_ms, end_ms)`, which passes `startTime`/`endTime`/`limit` through the shared `_public_request` (same rate limiter and error handling — a second httpx client would mean a second blind spot). **`net_r` is the number to trust.** The replay scans every closed 5m candle, uses advancing per-timeframe close cursors and cached hourly context, and serializes one simulated position per symbol until the exit candle closes. It does not model shared portfolio slots. Entries can require configurable directional trade-through in basis points (`--entry-penetration-bps`; zero preserves touch-fill baseline); stops gap-fill at the adverse bar open, and the entry candle can stop a trade but cannot earn a target or update trailing extrema. The CLI can mirror per-strategy enablement. These are OHLC-based sensitivities, not queue/partial-fill simulations. `tests/backend/test_backtest_trust.py` pins scan cadence, no overlap, timeframe alignment, conservative fills, and that the test-only lookahead probe reads future candles.
- **Execution cost assumptions live in `backend/core/cost_model.py`**: current account-calibrated taker fee 0.045%, maker fee 0.018%, and assumed slippage 0.01% per side (2026-10-20). The taker rate uses the account commission schedule and account-wide fills; those fills are not necessarily bot fills. The measured commission conversion averaged ~0.0446% of notional over 312 fills in seven days. Round-trip cost is modeled as 0.11%; it is an estimate, not a promise of realized execution. `scripts/strategy_compare.py` imports the shared taker and slippage constants. Historical research using 0.092% is superseded for cost-sensitive comparisons.

  - **`exchange_sync`'s day key and window are both UTC now (fixed 2026-10-18)** — it used to group by `DATE(closed_at)` (session-LOCAL) while `daily_summary.date` is written in UTC by the accumulator, and to filter on `closed_at >= :cutoff` (a **timestamp**). Two bugs: (a) on a host east of UTC the group key became the LOCAL day, so `WHERE daily_summary.date = t.d` overwrote **today's UTC row with a partial day**, which on a losing day pushed `used_r` back **under** the limit and silently re-opened an allowance the breaker had already consumed; (b) the timestamp window truncated the boundary day, so a complete day was overwritten with a partial aggregate — trades silently dropping out of the very total the breaker reads. Both the key and the filter are now `(closed_at AT TIME ZONE 'UTC')::date`, and the window is filtered on the **date** via `:first_day`, widening it to ~72h of days so no touched day is ever partial. Understating a losing day is the failure that matters; recomputing a couple of extra whole days is harmless because the statement is idempotent. **Do not revert to a bare `DATE(closed_at)` or a timestamp cutoff.** Pinned by `TestExchangeSyncGroupsByTheUtcDay` and `TestExchangeSyncSourceContract`.
  - **`exchange_sync` must never write an R derived from an implausible risk basis** (2026-10-18): the per-trade loop recomputes `pnl_r = exchange_pnl / (initial_risk_distance * quantity)`. `initial_risk_distance` is NOT reliably ~1% of equity — several positions carry a stored 1R of $0.015–$0.46 against an intended ~$2.21, so the division produced absurd multiples: a $1.36 trade became **+92.69R**. Pinned by `TestExchangeSyncWillNotFabricateR`, including a source contract that the cap is actually *used* — a constant nobody references is how the unguarded version looked protected. **Do not raise the cap to "fix" a trade that trips it; that trade's risk basis is wrong.**
- **`exchange_sync` is MANUAL-ONLY** (2026-10-18): a `POST /api/settings/exchange-sync` route with **no scheduler and no internal caller** — nothing in `bot_engine`'s main loop or `main.py` invokes it. This is how a `-1.09R` loss sat missing from Oct 17's `daily_summary` while the Trade Log showed it. No safety impact — `check_and_enforce_limit` never reads the column, only the dashboard's `limit_hit` display does — but it must not be read as "the bot halted here".

- **`used_r` is NET and that is deliberate** (2026-10-18): `max(0, -total_pnl_r)`, so only a losing day consumes R and a winning day can never trip the breaker. Gross-loss counting (wins never offset) was proposed by the user and **declined**: at the live 53% loss rate the third loss arrives after ~5-6 trades against `max_daily_trades=12`, which would halt before the trade cap on most days and roughly halve the rate at which the per-strategy sample accumulates. **Do not "fix" this** without that trade-off being re-agreed. `exchange_sync`'s SQL deliberately does not spell the `max()` — it excludes winning days because `limit_r` is strictly positive, and the shared clamp (`limit_r_from` only ever returns `(0, MAX]`) is what keeps the two spellings equal; the comment in the source says so, do not rewrite it into `GREATEST(0, -total_r)` for symmetry.
- **`used_r_from` fails CLOSED on a non-finite total** (2026-10-18): `max(0.0, -float("nan"))` is **0.0** — every comparison against NaN is False — so an unusable `total_pnl_r` silently read as "nothing consumed" and disabled the breaker for the day, the exact mirror of the NaN-limit case `limit_r_from` rejects. A non-finite value now returns `math.inf`, so `used >= limit` holds on every finite limit and the bot **stops**. Rule for this codebase: **an unreadable number must halt, never release** — the same posture as a rate-limited exchange response meaning UNKNOWN, never flat.

It happens to fail closed, so nothing is currently unsafe — but it is a second spelling of a live-money rule. Tracked as a follow-up; **do not delete it silently** and do not let it gain a caller.

A failed database write returns 503 and leaves the guard untouched; repeated reset requests must update the same setting row rather than insert a duplicate. - **`/performance/strategies` vs `/performance/strategies/breakdown`** (2026-10-18): two different things sharing a path prefix, deliberately. `/strategies` returns `{bucket, count}` R-distribution pairs — the frontend reads that exact shape for the histogram, so it must never start grouping by strategy. `/strategies/breakdown` is the per-strategy attribution table. ### Architecture notes

- **Scan loop must not make a signed request per symbol** (rate-limit guard, 2026-10-17): `_scan_and_evaluate` used to call `orders.get_current_position(symbol)` (a signed `positionRisk`) once per enabled symbol — ~24 calls per pass — which tripped Binance's IP rate limit (`-1003` → HTTP 400/**429**) and blanked EVERY signed call for ~60s (the limit self-clears), making the bot look dead. It now fetches ALL open positions **once per pass** via `OrderService.get_all_open_positions()` (one `positionRisk` returns every position) and re-uses the dict for the "already have a position" check — ~1 signed request/scan instead of ~24. Regression test asserts 1 bulk fetch + 0 per-symbol calls over a 24-symbol pass. Rule: **any per-symbol loop over `symbols` must not issue a signed Binance call per iteration** — batch it (one endpoint returns all) or move it behind the cheap local filters. NOTE: `evaluate_signal` still issues one signed `positionRisk` PER PENDING signal (~7 weight each, measured ~307/2400 per min total) — it is the remaining signed source that scales with signal count, not symbol count.
- **The high-frequency paths must not touch the database** (2026-10-17): the bookTicker handler fired 10-100+/sec and ran a fresh session + `SELECT * FROM positions` per message — hundreds of queries/sec on the pool the scan loop and the 30s pass need. The per-symbol lock does NOT throttle it (a local SELECT is ~1ms, so the lock is free >99% of the time). This is the same event-loop starvation class as the old WS task leak and, unlike a rate limit, produces no diagnostic signal. `_get_open_positions` now refreshes `_open_positions_cache` and the tick path reads `_cached_open_positions()`. **Rule: anything called per message, per tick or per row must read a snapshot, not the database.**
- **Closing a position must CLAIM it atomically** (2026-10-17): `_close_position` is reached from the WS tick path, the 30s REST pass and the 5-min reconcile. Its old `status == "OPEN"` check was a read-then-write spanning `get_position_income` + `session.get(Signal)`, so two paths could both observe OPEN and both commit a Trade — duplicating the trade and DOUBLING the daily R total, which can trip the -3R hard stop on phantom R and halt trading for the day. It now claims the close with `UPDATE positions SET status='CLOSED' WHERE id=:id AND status='OPEN'` and bails on `rowcount == 0`, rolling back its own Trade. The in-memory check remains only as a cheap fast path.
- **Fail closed when the exchange state is unknown** (2026-10-17): three call sites read "I couldn't reach the exchange" as "there is no position". A rate-limited `_signed_request` returned `{}` (now raises `BinanceAPIError(-1003)`); `get_lot_size` returned `{}`, silently disabling qty/price rounding so an unrounded SL was rejected and the filled position had no stop (now raises, and caches filters per symbol); `_flatten_if_unprotected` returned `None`/`[]` on error, so a blip could close a protected position or orphan an open one (now returns `bool` — `False` means "state unknown or deliberately left open", and the caller keeps the DB row OPEN for reconcile adoption). **Rule: in this codebase an empty/falsy exchange response means UNKNOWN, never flat — and a sweep that cannot identify the order to keep must do nothing rather than cancel blindly.**
- **Manual stop changes go through the exchange** (2026-10-17): `PATCH /api/positions/{id}` wrote SL/TP to the DB only, so Binance's resting algo stop was unchanged while the dashboard showed the new one — a naked position by another route. It now places `modify_position_stop` first and commits the row only on success (502 otherwise), sweeps superseded stops, and validates the stop/target are on the correct sides for the position's direction.
- **Sweep the exchange for stops, not the orders table** (`f3810be`, 2026-10-17): the trail path posts a new STOP_MARKET but never writes its `algoId` back to `orders`, so a table-scoped cancel only ever found the ORIGINAL entry SL and every trailed stop stayed armed (observed: 7 stacked stops on OPUSDT; the widest one closed the position before any profit-lock stop could). `_cancel_active_sl` now sweeps `openAlgoOrders` for the symbol, keeping `keep_algo_id`. **When `keep_algo_id` is unknown the sweep is skipped entirely** — cancelling blind would remove the stop just placed and leave the position naked, which is strictly worse than extra reduce-only stops.
- **Session factory, not sessions**: `main.py init_bot` hands every component (`BotEngine`, `PositionManager`, `DailyResetService`, `StrategyService`, `SignalService`, `OrderService`) the `AsyncSessionLocal` FACTORY. AsyncSession is not task-safe — the scan loop runs concurrently with request handlers on the same loop, so each operation opens a short-lived session. Never reintroduce a long-lived shared session.
- **Daily loss breaker pauses entries without terminating the scan loop**: a tripped limit persists `daily_loss_limit_hit` (creating today's summary row when the trip came only from unrealized PnL), blocks new entries for the rest of that UTC day, and keeps the loop alive to observe midnight and resume. A reconstructed service restores today's persisted latch. Existing live positions remain under their exchange stops; do not call `BotEngine.stop()` from the daily breaker, because a stopped loop cannot reach its own reset check.
- **Paper mode records everything**: simulated fills + OPEN Position rows + signal TRIGGERED. This deliberately deviates from PHASE3_STEP3's "no records in paper" because PHASE3_STEP7's 72h paper run and the dashboard need the data.
- `AlertService` methods are async (they broadcast via `ws_manager`); the engine-side callers await them.
- 2026-10-11 second-pass fixes: `/fapi` paths + depth endpoint + reduce-only closing orders, inverted R:R math in FVG/CHoCH/3-candle evaluators, FVG fill semantics + zone bounds, BotEngine/PositionManager wiring, `/ws` route + double-accept + receive-loop disconnects, async AlertService, `get_status` un-awaited coroutine. All covered by `tests/backend/`.
- **Open-position pricing parity (2026-10-15)**: `routers/position_pricing.py` serves both position endpoints. LIVE mode uses the engine's authenticated Binance client (a fresh `BinanceService()` has no creds — it 401s signed endpoints) and reads `positionRisk` per symbol: exchange entryPrice/positionAmt/markPrice/unRealizedProfit/leverage replace the DB recomputation, plus `unrealized_pnl_pct` = PnL ÷ initial margin (Binance's ROI definition). PAPER mode computes from the **mark price** (`fapi/v1/premiumIndex` — the Binance app default; `fapi/v1/ticker/markPrice` never existed). Live entries record the exchange's executedQty + avgPrice on the position row (`get_order` fallback, strictly best-effort — a failed fill fetch must never abort an already-filled entry).
- **Reconciliation runs BOTH directions** (`PositionManager._reconcile_exchange_positions`, every 5 min in live mode): exchange-only positions → recorded OPEN **with the exchange's own resting SL/TP adopted** (reads the TRANSFORMED `get_all_positions()` keys — `quantity`, not raw `positionAmt`; the raw-key read silently skipped every position, so this direction never worked until 2026-10-15); DB-OPEN rows with no exchange position → closed as `EXTERNAL_CLOSE` (resting SL/TP cancelled, NO redundant market close). Rows younger than 120s are skipped (positionRisk race). `get_position_income` is scoped to the position's open time so a close never sums an earlier same-symbol position's PnL.
- **Never assume an engine-detected exit filled on the exchange**: `_close_position` treats TP_HIT/SL_HIT as exchange-side fills, so it calls `_ensure_flat()` — re-reads positionRisk and market-closes any leftover (a rejected BE-stop placement once left XRPUSDT open and naked for 1.5h while the DB showed it closed). `_trail_stop_to_be` places the new stop BEFORE cancelling the old and reverts the DB stop if placement fails: the DB stop must never be tighter than the exchange's.
- **BE-trailing is price-based** (user-approved 2026-10-15 after the audit): `_check_be_trailing` trails to break-even once the trade is `be_trail_trigger_r` R in profit (setting, default **+0.5R**, slider in Settings) — one-way, and only when `initial_risk_distance` is known. The earlier "new BOS after entry" rule was rarely satisfied, so ~80% of trades rode to the full structural stop; at that stop-out rate full -1R losses make expectancy negative (`0.8×(-1R) + 0.2×3R = -0.2R` vs `+0.6R` with the BE stop).
- **Live entries are LIMIT orders at the entry-zone midpoint** (user-approved 2026-10-15): "the planned price or no trade". MARKET fills landed up to 1% outside the zone (degrading the planned R:R) and, when the market had already passed the stop, produced an invalid SL that Binance rejected with 400 — aborting the flow after the entry filled and leaving the position NAKED (live XRPUSDT/BTCUSDT, unprotected for hours). `_enter_with_limit` polls the order briefly, cancels + skips when unfilled, and the Position row is created only AFTER the fill (exchange-truth entry/qty from the start).
- **The SL/TP are re-validated against the MARK price AFTER the fill** (user-approved 2026-10-17, "Option A"). Gate 4b checks the sides against the zone before the limit is sent, but the market can cross the stop in the ~1s between the fill and the SL placement — Binance then rejects the already-in-the-money conditional order with 400 and the fill sits naked until the safety net flattens it (live APEUSDT LONG: filled 0.14860 with the stop at 0.1484, SELL STOP 400 one second later, 1592 APE flattened). `evaluate_signal` now re-reads the **MARK** price (`get_mark_price` / `fapi/v1/premiumIndex` — Binance triggers conditional orders on contract price, the same source `PositionManager._check_positions` uses) after `_update_position_fill` and, if the stop or target is no longer strictly on the correct side, places NOTHING: it flattens at market via `_flatten_if_unprotected`, records the realised Trade via `_close_position_row`, marks the signal SKIPPED and returns SKIP (`Setup void after fill: …`). Three rules follow from this: (a) **EQUALITY is invalid** — a trigger condition already met at submission is rejected ("would immediately trigger"), so a LONG stop must be strictly below the mark and its target strictly above (reverse for SHORT); (b) **no fallback to the last trade price** — unlike the TP/SL hit check, a last price on the correct side with a mark beyond the stop re-authorises the rejected SL, so an unreadable mark is UNKNOWN and fails closed; (c) the check is LIVE-ONLY, because paper fills are simulated at the plan price. Re-anchoring/widening the stop and cancel-and-refill-at-market were considered and rejected — "the planned price or no trade" applies to the stop too.
- **`get_status` must not hardcode `open_positions`** (2026-10-17): it returned a literal `[]`, so `/bot/status` reported a flat account while three positions were open (observed live). Nothing in the dashboard reads the key — that page uses `/dashboard/overview` — so the lie only misled other consumers and an operator with curl. `_open_position_summaries()` prefers `PositionManager._cached_open_positions()` (the same snapshot the bookTicker tick path reads — no query per call) and falls back to `_open_positions_from_db()` (one indexed `status='OPEN'` query) when the cache is empty, because the cache returns `[]` both for a genuinely flat account AND before the first 30s pass — "nothing open" must never be inferred from "not yet refreshed". A read failure degrades to `[]` with a WARNING rather than 500-ing the endpoint. Rows are coerced to plain floats/ISO strings so the response stays JSON-serialisable (the `Numeric` columns would otherwise serialise as `Decimal`).
- **Every close path must notify `DailyResetService`** (2026-10-17): `StrategyService._close_position_row` records a `FLATTENED` Trade but never notified the daily service, so the R only reached the accumulator via the 48h exchange-sync recompute — and that total is what enforces the -3R breaker, so it understated reality in between. `StrategyService` now takes `daily_reset` by **constructor injection** (exactly how `PositionManager` receives it; `main.init_bot` builds ONE `DailyResetService` and hands it to both, moved above the `StrategyService` construction). **This cannot double count, and the reason is load-bearing:** `update_daily_summary` is an **INCREMENT** (`total_trades + 1`, `total_pnl_r + pnl_r`, never reads `trades`) whose only other caller is `PositionManager._close_position` — a different close path that cannot also flatten this row. The 48h recompute in `routers/settings.exchange_sync` does **not** call it; it runs one raw-SQL `UPDATE daily_summary SET ... FROM (SELECT ... FROM trades GROUP BY DATE(closed_at))`, which **sets absolute aggregates and is therefore idempotent** — it overwrites, never adds. If either half of that changes, re-check for double counting. The notification sits AFTER the Trade commit and in its own try/except: a failure must never undo the recorded Trade (130f16e's contract).
- **Every row `StrategyService` writes is tagged with `self._mode`** (2026-10-17): `_close_position_row` read `self._mode`, but the attribute was never initialised or assigned anywhere (only `PositionManager` had it), so the `AttributeError` was swallowed by that method's broad `except Exception` — no Trade row AND an orphaned OPEN Position for a position already flattened on the exchange. It is now initialised to `"paper"` and set at the top of `evaluate_signal`.
- **The backend serves the built SPA** (2026-10-16, NPM cut-over): FastAPI mounts `frontend/dist/assets` and registers a `/{full_path:path}` catch-all returning `index.html` (client-side routing) — Nginx Proxy Manager is a dumb reverse proxy that cannot serve files or do try_files. API/WS routes are registered BEFORE the catch-all and win by order; the handler also hard-guards `api/|ws|health|docs|openapi` prefixes so a future route reorder cannot swallow the API.
- **Strategy toggles are now consumed by the scan** (2026-10-16, DECISION.md D1): `strategy_fvg_enabled` / `strategy_3candle_enabled` / `strategy_choch_enabled` existed in the Settings API but were never read — a 'disabled' strategy kept firing (2,804 wasted FVG signals). `scan_symbol` now gates each detection block on its flag (default True). FVG is disabled in production (stop geometry produced 15.6% targets, -0.397R/trade live, 0/5).
- **Skipped signal persistence is deduplicated by setup and normalized reason for one signal-expiry window** (2026-10-20): only PENDING reserves the coarse `(symbol, strategy_type, direction)` slot. Repeated SKIPPED candidates with the same zone and reason template are not written again until `signal_max_age_minutes` elapses; the changing numeric ADX reading is normalized for the dedup key, while the first row retains its full readable reason. If the same setup passes its filters, it is still persisted as PENDING immediately. A read-only production sample had 8,683 EXPIRED 3CANDLE rows but only 33 distinct setup-zone signatures in 24h (max 633 repeats); normalizing ADX reduced the observed five-bucket reason-key upper bound from 297 to 95. This reduces DB churn without reserving a skipped setup or changing entry eligibility. The local change is not deployed or regression-tested yet.
- **OB+FVG is wired into the scan** (user-approved 2026-10-17, `signal_service.detect_obfvg_candidates`): a 1h Fair Value Gap only fires when a confirmed same-direction Order Block on the 5m series overlaps its zone — `fvg_within_order_block(..., current_idx=len(k5m)-1)`. Plain FVG is disabled at -0.397R/trade; the OB confluence is the differentiator (+0.432R ungated / **+0.315R with the live trend gate**, 20 symbols, R:R 3.0, 84 trades / 3.5 days). It then passes through the SAME filter chain as every other strategy (trend bias, trend strength, RSI, volume, R:R) — no bypass.
  - **Freshness is the load-bearing constraint.** The backtest entered each gap at the first 5m bar after its forming hour closed. Live has no historical index to enter at, so eligibility is bounded by RECENCY instead: only FVGs on the last `strategy_obfvg_max_age_bars` CLOSED 1h bars (default 2). Raising this is NOT free — it widens the trade away from what was measured, and lowering it toward 0 starts missing gaps at the 60s scan cadence.
  - It is a 1h pattern, so the volume filter must read `k1h`, not `k5m` — the routing check is `strategy_type in ("FVG", "OBFVG")` (a bare `== "FVG"` silently fed it 5m volume).
  - Evidence is thin (3.5 days; `--days 45` yields ~3.5 days because Binance caps unpaginated klines at 1000 bars). Default is ON per user decision — treat early OBFVG results as unvalidated.
  - The backtest harness had a **lookahead bug** in strategy C, now fixed via `fvg_entry_idx_5m`: an FVG at 1h bar `i` is only knowable at that hour's CLOSE (5m `i*12+11`), but the exit scan started at `+1`. It inflated expectancy from +0.315R to +0.402R.
- **Setup validity + side awareness** (audit fixes): `evaluate_signal` gate 4b skips a setup whose stop has already been breached by the market (or whose target is already reached) — for LONG the stop must sit below and the target above the market, reverse for SHORT. `RiskService.validate_rr_ratio(..., direction=)` is side-aware; the old `abs()` version scored a LONG whose stop was ABOVE its entry at **93:1** and executed it.
- **`_flatten_if_unprotected`**: after ANY live-flow failure (or an unconfirmed limit fill) the exchange position is checked — a position with no resting STOP_MARKET is market-closed immediately; one WITH a stop is left for the reconcile to adopt (with its SL/TP). Before this a failed flow dropped the DB row and left the position naked.
- **R:R is validated at the price we will actually get** (user-approved 2026-10-15): the gate runs against the zone midpoint (paper fill) and, for live, against the current market price before the limit is placed — XRP planned 3.25:1 at the midpoint but the market was 1% away (~1.1:1). `_update_position_fill` recomputes the frozen `initial_risk_distance` from the actual fill, so `pnl_r` reflects the risk actually taken.
- **Position sizing has TWO constraints**: `calc_position_size` (risk-based: qty = balance × risk_percent / stop-distance) is then capped by `cap_position_notional` at `max_position_notional_pct` of balance (Settings UI, default 50). The cap is a hard CEILING, so whenever it binds the effective risk falls below `Risk Per Trade` — with ~1% stops a 50% cap turns a 5% target into ~$1-2 per trade (the live reality on 2026-10-15). `StrategyService` logs a WARNING with the symbol and the resulting effective risk % whenever the cap binds; to honor the risk target the cap must be ≥ risk_percent / stop% (e.g. 5% risk with ≥1% stops needs a 500% cap).
- **Configured leverage is currently metadata only** (audited 2026-10-20 on deployed `9cefc0e`): `leverage_btc` / `leverage_alts` are copied to the Position row, but `BinanceService.set_leverage()` has no call site. A read-only `fapi/v2/positionRisk` query using the app’s Account-table credentials returned 5× cross margin for all seven enabled symbols, including BTC despite `leverage_btc=10`, with zero open exposure. Exchange leverage may be configured outside the app and can differ from Settings. `max_position_notional_pct` caps each position independently; it is not an aggregate margin budget across `max_positions`. Do not use configured leverage as proof that the order uses that leverage or that all slots are fundable. Any wiring change must verify exchange state and budget aggregate initial margin before placing the entry.
- **Settings hot-reload**: `PUT /settings/trading` rewrites the shared settings dict in place (`live.clear(); live.update(await load_bot_settings(db))`) — every engine component is handed that same dict by `main.init_bot`, so slider changes (risk, notional cap, filters, guards) apply to the RUNNING engine. Before 2026-10-15 the engine kept its startup snapshot until a service restart.
- **Exchange errors must carry Binance's own code/msg, and must never carry the signature** (2026-10-17): both request paths used `resp.raise_for_status()`, which (a) throws the body away — a rejected order surfaced as `Client error '400 Bad Request' for url '...'` while the actionable `{"code":-2021,"msg":"ReduceOnly Order is rejected..."}` was never read, and (b) renders the FULL signed URL into the exception, so `signature=<hmac>` and the API key landed in `journalctl`. Both paths now call `_error_from_response(resp, method, path)`: a JSON dict body becomes `BinanceAPIError(code, f"{msg} [{method} {path}]")`, anything else (Binance serves an HTML page for some 404s) falls back to the HTTP status with a **redacted** URL. Redaction is the module-level `redact_url()`, applied by key NAME (the signed query string is rebuilt per request, so a value-based scrub would miss every signature) and it DROPS the parameter rather than blanking it, so no raised or logged string ever contains `signature=`. The 200-with-`code`/`msg` path and the 3×429 exhaustion path are unchanged and separately pinned.
- **`_signed_request` code semantics**: algo endpoints return `{"code": "200", "msg": "success"}` on SUCCESS — `code` arrives as a STRING, so compare numerically (`int(data["code"]) != 200`); the naive `data["code"] != 200` raised on every successful `cancel_algo_order`. The raise was client-side only (the DELETE reached Binance), but callers logged success as failure and misjudged outcomes.
- **Orphan sweep on close**: `_cancel_exchange_orders(position_id, symbol)` cancels the orders-table records, then sweeps `openAlgoOrders` for the symbol (new `get_open_algo_orders`) — orders placed outside the orders-table logging (BE-trail stops, manual re-placements) are invisible to the position-linked pass and would otherwise outlive the position and close a FUTURE position prematurely (observed live: a BE-trail stop survived a TP_HIT close). The engine holds one position per symbol, so at close time every resting algo order on the symbol is an orphan.
- `_round_qty`/`_round_price` are Decimal-based: `math.floor(qty/step)` mis-floors exact float multiples (89.3 → 89.2), leaving a 0.1-lot slice uncovered by reduce-only SL/TP.
- `Position.opened_at` defaults to aware UTC now (was naive `utcnow()` → −2h skew that corrupted the reconcile age guard and income windows).

- **Weekly full-reset cutoff survives restart and expires at UTC midnight** (2026-10-20): `/api/bot/reset-weekly-guard` persists `weekly_reset_from`; `WeeklyDrawdownGuard.check_weekly_drawdown()` loads that timestamp once before querying trades, or a restart re-counts the historical losses the operator reset past. The cutoff expires after its UTC calendar day, returning the guard to the natural Monday window. If the setting cannot be read or parsed, use the natural Monday window (fail closed). `tests/backend/test_weekly_drawdown.py` pins restoration and use of the persisted cutoff in the trade query.

### Coding Rules
- Use async/await for all I/O operations
- Never log or expose API keys/secrets
- All Pydantic models use `ConfigDict` (not `class Config`)
- Database sessions via dependency injection (`get_db`)
- Bot control commands (start/stop) require authenticated user
- **Bot lifecycle owns one scan loop**: repeated `/api/bot/start` requests in the current mode are idempotent; a mode switch or start during stop returns HTTP 409. A stop requested from inside the scan loop must not cancel/await itself, and a new loop cannot start until the prior one has exited. A stop invalidates an in-flight start before it can create a task.
- **Same-scan exposure is included in entry guards**: after a successful execution, update the scan's occupancy map so later symbols in that pass see the new same-symbol and correlation exposure. Keep it separate from the initial live mark-to-market snapshot used by the daily breaker.
- **Live portfolio stop-risk budget**: `max_aggregate_risk_pct` (default 3%) caps the sum of each open position's quantity times frozen initial stop distance, then sizes a new entry only from the remaining budget. Missing or invalid stop-risk bases fail closed. This is a stop-loss estimate, not a guaranteed maximum loss; gaps, fees, slippage, and exchange failures can exceed it. `StrategyService` requires an account-wide exchange snapshot in live mode. A protected fill surviving a failed later leg must be included in same-scan occupancy; unknown exposure aborts the rest of that scan pass. Failed-flow cleanup must also reject malformed, non-finite, nonpositive-trigger, negative-quantity, or side-unknown exchange stop/position snapshots without guessing a close side or quantity.
