# Full codebase review — 2026-10-17

Scope: `backend/` (8.4k LOC), `frontend/src/`, `scripts/`, `tests/`.
Context: live-money Binance Futures bot. Review followed commit `71399af`
(the rate-limit fix). 205 tests passing at review time.

Method: four parallel deep reviews (position_manager, strategy/risk services,
binance service + WS, auth/security) plus a frontend review, each finding then
independently re-verified against the source before inclusion. Anything not
reproduced by direct inspection is marked SPECULATIVE.

## Tier 1 — confirmed, costs money or blinds the operator

### 1.1 Trail stops stack: every trail after the first leaves the previous stop armed
`backend/core/position_manager.py:527,558-584`

`_trail_stop_to_be` places a new exchange stop via `modify_position_stop` and
discards the returned `algoId`. `_cancel_active_sl` cancels only orders recorded
in the `orders` table for that `position_id` — which holds the *original* entry SL.

Pass 1 (BE, +0.5R): place stop A (unrecorded); cancel entry SL (recorded) → A armed.
Pass 2 (profit lock, +1R): place stop B (unrecorded); "cancel" retries the dead
entry SL → -2011 swallowed at line 582 → **A and B both armed**.

`A` (lower) triggers first. Every "profit-locked" trade books at the first trail
level, so profit-lock is a no-op that still posts exchange orders.
`_check_profit_trailing` re-fires each pass price makes a new high, so stops
accumulate over the position's life — the same orphan-stops-at-old-prices class
documented at line 713. Existing test covers only a single trail.

Fix: cancel the symbol's resting STOP_MARKET algos via `get_open_algo_orders`
before re-placing, or log the new stop with its `position_id`.

### 1.2 Double-close race → duplicated trades, doubled daily R, phantom -3R trip
`position_manager.py:280-299` (locked) vs `301-353`, `85-133` (unlocked), guard at `606-609`

Only `_on_tick` takes `_check_locks[symbol]`. `_check_all_positions` (30s) and
`_reconcile_exchange_positions` (5min) call `_close_position` unlocked. The
`status == "OPEN"` guard is a non-atomic read-then-write spanning two awaits —
`get_position_income` (HTTP) and `session.get(Signal)`. Both sessions can read
OPEN and both commit.

Verified: the guard-to-commit window contains exactly those two awaits and no
row-level lock or conditional UPDATE. Two sessions both pass → two Trade rows →
`update_daily_summary` twice → daily PnL/R doubled → the -3R hard stop can trip
on phantom R and halt trading for the day.

Fix: `UPDATE positions SET status='CLOSED' WHERE id=:id AND status='OPEN'`,
check rowcount, bail before inserting the Trade.

### 1.3 Live market-close failure leaves a naked position
`position_manager.py:731-733`, `_market_close:813-823`

Protective orders are cancelled **first**, then `_market_close` is called — and
it swallows every exception with `logger.error` only. If the close fails (429
after retries, network, or `_round_qty` raising below `minQty` on a dust
residual) the exchange holds an open position with **zero SL/TP** while the DB
says CLOSED. Same for `close_all_positions`.

Fix: place the close first; on failure re-place a protective stop, alert CRITICAL, force a reconcile.

### 1.4 `PATCH /api/positions/{id}` writes SL/TP to the DB only — live positions stay unprotected
`backend/routers/positions.py:107-113`

Assigns `position.stop_loss` / `take_profit` and commits. Never calls
`binance.modify_position_stop`, which exists and is used by the BE-trail path.

The operator moves a stop on the dashboard; the UI reflects it; Binance's resting
algo stop is unchanged. The position they believe is protected is naked — the
exact `_flatten_if_unprotected` failure class, reintroduced via a user-facing
route. It also corrupts the BE one-way comparison, which reads `position.stop_loss`
as its baseline. `PositionUpdateRequest` has no bounds and no side check, so a
LONG's stop can be set above the market.

Fix: in live mode call `modify_position_stop` first, commit the row only on success. Add side-aware validation.

### 1.5 Resting GTC entry limit survives stop/restart → later fills naked
`strategy_service.py:491,500-524`

`_enter_with_limit` places a **GTC** limit and cancels only on the normal return
path. `asyncio.CancelledError` is a `BaseException`, so `except Exception` at 503
does not catch it — pressing Stop or a deploy during the 12s wait leaves the
order armed. Nothing sweeps regular open orders: `get_open_orders` exists at
`binance_service.py:461` with **zero callers**; the reconcile reads positions and
algo orders only.

The order fills later into an unmanaged position with no Position row, no SL, no TP.

Fix: cancel in a `finally` / `except CancelledError`; add a startup sweep of open orders.

### 1.6 The failed-flow handler closes the DB row even when the position was deliberately left open
`strategy_service.py:322-334` vs `549-553`

`_flatten_if_unprotected` deliberately does NOT flatten when a resting SL exists
("leave the position for reconcile to adopt"), then line 333 closes the DB row
that the reconcile would have adopted.

SL succeeds, TP fails → position open with an SL, **no TP**, **no OPEN row**, so
nothing manages it. Reconcile later adopts it with `initial_risk_distance=None`,
and `_check_be_trailing` returns immediately on `risk is None` (line 372) — so
it can never be trailed again and must ride to the full structural stop.

Fix: have `_flatten_if_unprotected` return whether it flattened; only close the row when it did.

### 1.7 `PUT /settings/trading` has no bounds — the -3R stop can be switched off
`backend/routers/settings.py:140-151`, `backend/schemas/settings.py:44-67`

`config.py` validates with `ge`/`le` (`RISK_PERCENT 0.5–2.0`, `CHECK_INTERVAL 10–300`,
`MAX_POSITIONS 1–10`, `RR_MIN 2.0–5.0`). `TradingSettingsUpdate` declares every
field as a bare `float | None` with **no constraints**, and the values are written
straight to the DB and hot-reloaded into the running engine. The config bounds are
never consulted on this path.

Reproduced:
```
TradingSettingsUpdate(daily_loss_limit_r=9999.0, check_interval_seconds=0, rr_min=0.01)
  -> accepted
DailyResetService(...).get_limit_r() = 9999.0   (production: 3.0)
sleep_time = max(0, 0 - 3.2) = 0                -> scan loop spins with no delay
```
`check_interval_seconds: 0` is a self-inflicted rate-limit ban. Note also that
`get_trading_settings` clamps `strategy_obfvg_max_age_bars` on **read**
(`max(0, ...)`, line 124) while `load_bot_settings` feeds the engine the raw row —
response clamping is not enforcement.

Fix: same `Field(ge=, le=)` bounds on the update schema; reject on write. Hard-clamp inside `get_limit_r()` and `_main_loop` so a bad DB row can never disable a guard.

### 1.8 Rate-limited requests read as "flat" — `_signed_request` returns `{}` after 3× 429
`binance_service.py:104-134`, `get_position:267-278`

The 429 branch `continue`s without raising, so three consecutive 429s fall out of
the loop to `return {}`. `get_position` iterates that and returns `{}` —
**indistinguishable from "no position"**.

At `position_manager.py:835-839` `_ensure_flat` calls `get_position` after a
detected exit; rate-limited → qty 0 → returns without flattening. The DB records
CLOSED while the exchange holds an unprotected position. Via
`order_service.py:44-46` the same failure makes the scan loop believe no symbol is
held and open a **second** position on an exposed symbol.

Fix: raise `BinanceAPIError(-1003, ...)` on the exhausted-retry path so callers can distinguish "unknown" from "flat".

### 1.9 bookTicker tick opens a DB session and runs a SELECT on every message
`position_manager.py:291` → `_get_open_positions`

The per-symbol lock does **not** throttle this: a local SELECT completes in
~0.5-2ms while bookTicker fires 10-100+/sec, so the lock is free >99% of the time.
Hundreds of SELECTs/sec sustained on the pool the scan loop and 30s pass need —
the same event-loop starvation class as the WS task leak, and it will present as
"the bot went unresponsive" without any rate-limit signal.

Fix: cache the open-position snapshot (refreshed by the 30s pass, ~1s TTL), read it in the tick handler.

## Tier 2 — confirmed, real defects, lower money impact

### 2.1 Liquidation price and margin-at-risk are always `$0.00`
`backend/routers/dashboard.py:_format_position`, `backend/routers/positions.py:_format_position`

`apply_pricing` computes both (`position_pricing.py:103,108`) and the schema
declares them (`dashboard.py:72-73`), but **neither `_format_position` passes
them**, so Pydantic defaults them to `0.0`. Commit `ed2bcf1` added the
computation, the schema fields, the store mapping and the UI columns across four
files — and never wired the two producers. The Overview has displayed
`Liq Price 0.000000` / `Margin at Risk $0.00` on every live position since.

Fix: pass `liquidation_price=px["liquidation_price"], margin_usd=px["margin_usd"]` in both.

### 2.2 WebSocket never reconnects after a logout → login cycle
`frontend/src/api/websocket.ts:65-68`, `27`

`disconnect()` sets `shouldReconnect = false`; `connect()` never resets it. After
signing out and back in, the socket's `onclose` sees `false` and does nothing.
From the next drop until the tab is closed there is **no WS**: no SL/TP alert
toasts, no `position_closed` events. `connect()` also never closes an existing
socket, so repeated calls leave zombie sockets each with its own reconnect chain.

Fix: `this.shouldReconnect = true` as `connect()`'s first statement; early-return if `readyState` is OPEN/CONNECTING; `close()` any prior socket.

### 2.3 `checkAuth`'s non-401 branch signs the user out, contradicting its own comment
`frontend/src/store/authStore.ts:87-89`

The comment says a transient error should not wipe the session; the `else` branch
sets `user: null`, so `RequireAuth` redirects to `/login`. A 502 during a deploy
bounces the operator to the login screen with live positions open.

Fix: keep the stored user/token on non-401 and surface a "connection lost" state.

### 2.4 Starting LIVE has no confirmation, no error surface, no in-flight guard
`frontend/src/pages/Overview.tsx:161-172`

The most dangerous control in the app — real mainnet orders at the configured
risk — is the only irreversible-feeling action without a confirm dialog (Close and
Close All both have one). The handler returns a promise that is never caught, so a
refused start looks like a no-op, and a double-click fires two starts.

### 2.5 Operational actions fail silently
`Overview.tsx:88-110`, `Settings.tsx:281-285,489-505`

Start/Stop has no catch; Close All, the settings save, and symbol toggles all
`console.error` only. Given the documented notional-cap override, a silently
rejected Risk Per Trade change is money-relevant.

### 2.6 Partial limit fill reported as a clean "not filled"
`strategy_service.py:500-524`

Only `FILLED` and the terminal cancelled set are recognised; `PARTIALLY_FILLED`
loops to the 12s deadline, cancels, returns `None`, and the caller writes "not
filled at the plan price" — never reading `executedQty`.

### 2.7 `_flatten_if_unprotected` fails open on both error paths
`strategy_service.py:536-540, 545-548`

`get_position` failure → `return` (no-op) and the caller then closes the row.
`get_open_algo_orders` failure → `algos = []`, which reads as "no stop resting" —
the condition that *authorises* a market close. A transient blip closes a
correctly-protected position.

### 2.8 `get_lot_size` silently disables rounding
`binance_service.py:326-338`, `_round_qty:349`, `_round_price:363`

Returns `{}` on any exception; both rounders then return the **unrounded** input.
One exchangeInfo timeout during a live entry → SL sent with unrounded quantity →
Binance 400 → the position is open with no stop.

### 2.9 `binance_ws.connect()` cancels the old listener after awaiting the new socket
`binance_ws.py:49-55`

`_open_socket()` is awaited **before** the old task is cancelled. That await yields,
the old `_listen` resumes on a closed socket, hits its `except`, and — because
`self._running` is still True — schedules its own reconnect. Narrow race, but it
is a residual of the task-leak bug in a second entry point.
Also: `_reconnect_delay` is never reset on success (line 116), so after a few
flaps every reconnect waits the full 30s.

### 2.10 `evaluate_signal` still issues a signed `positionRisk` per PENDING signal
`strategy_service.py:104`

The scan-loop fix removed the per-*symbol* call, but each PENDING signal still
costs a signed positionRisk (weight 5) + ticker (2) = 7. This scales with signal
count, not symbol count. Measured budget at 20 PENDING/scan: ~307 weight/min of
2400 — currently fine, but it is the remaining unbounded signed source and the
natural next trip.

### 2.11 Declared rate-limiter weights are wrong
`binance_service.py:173` (klines limit=200 → weight 2, declared 1), `:282`
(positionRisk → 5, declared 1), `:258` (balance → 5, declared 1). The local
1200/min budget is consumed at roughly half the true rate, so the limiter's
margin is illusory and it should not be relied on as the safety net. Also
`get_lot_size` downloads a full `exchangeInfo` (~1MB) on **every** order
placement — three per live entry — with no caching.

### 2.12 `GET /bot/status` returns 200 unauthenticated when the engine is uninitialised
`backend/routers/bot.py:140-148`

The `_bot_engine is None` early return precedes `get_current_user_from_cookie`.
The other four bot endpoints return 503 before auth, letting an anonymous caller
distinguish "engine down" from "not authorised". The existing
`test_unauthenticated_access_blocked` passes only because its fixture leaves the
engine initialised.

### 2.13 `DELETE /api/orders/{id}` cancels in the DB only
`backend/routers/orders.py:71-91` — sets status CANCELLED and returns ok while
the order stays armed on the exchange.

### 2.14 No token revocation; no authorization model
`auth_service.py:32-48`, `auth.py:45` — logout only deletes the cookie; the JWT
stays valid 24h. A `role` column exists and is returned by `/me` but **no router
reads it**, and there are no `user_id` columns anywhere, so any authenticated
account is a full administrator. There is no registration endpoint today, so this
is an operational invariant rather than an enforced control.

### 2.15 `/docs` and `/openapi.json` are unauthenticated
`main.py` — `FastAPI(...)` defaults register them unconditionally, giving an
unauthenticated map of every route including which ones move money.

## Speculated but not confirmed

- Profit/R:R display and unit handling across Overview/Trade Log/Performance is
  correct — `unrealized_pnl` USD, ROI ×100, `win_rate` not double-scaled, ascending
  chart series, no `getSeries()` misuse. The lightweight-charts fixes hold.
- Auth core is sound: HS256 pinned (no `alg=none`/algorithm confusion), `exp`
  enforced, secrets `Field(min_length=32)` with no default so the app fails closed.
  No SQL injection anywhere (all SQLAlchemy bound params, the one `text()` uses
  `:cutoff`). No plaintext credentials in any response or log. CSRF adequately
  mitigated by `httpOnly` + `Secure` + `SameSite=Lax`. SPA catch-all cannot
  traverse or shadow the API.
- Position sizing math is correct: `qty = risk_usd / price_diff`, Decimal
  throughout, `minQty` enforced.
- Gate 4 + midpoint LIMIT entry provably cannot produce a marketable-entry
  accident — a resting BUY requires `market > midpoint` while gate 4's lower bound
  gives `market ≥ zone_min·0.99`, so it cannot reduce an existing short. This part
  of the design is sound.
- No remaining path trips Binance's 2400/min. The `71399af` fix is real and
  verified: `get_all_open_positions()` is called exactly once before the loop and
  nothing inside the per-symbol body touches `positionRisk`.

## Suggested order

1. **1.1, 1.2, 1.3** — trail stacking, double-close race, naked-on-close-failure.
   All three are live-loss paths in the position lifecycle.
2. **1.7** — bounds on the settings schema. One file, closes a whole class.
3. **1.8, 1.9** — raise on exhausted retries; stop the per-tick DB hammer.
4. **1.4, 1.6, 2.7** — live paths that must go through the exchange before the DB.

6. **2.1–2.3** — the three operator-visible lies (margin $0.00, dead WS, spurious logout).
7. Tier 2 remainder, then Tier 3.
