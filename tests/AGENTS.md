Classes: `TestLimitRFrom` (sign, range bounds inclusive at `MAX`, non-numeric, missing key, NaN/inf), `TestUsedRFrom` (winning/losing/flat day, no row, NULL `total_pnl_r`, and **a non-finite `total_pnl_r` → `inf`, i.e. the breaker HALTS** — `max(0.0, -nan)` is 0.0, so the naive formula silently freed the day; the halting case is asserted through `check_and_enforce_limit` itself, not just the helper, because "used > 3.0" only means something if the caller enforces it), `TestTodayUtc` (resolves in UTC; no local resolution in the module), `TestServiceDelegatesToHelpers` (the service's `get_limit_r`/`get_daily_stats` bind the shared results), `TestDashboardAgreesWithBreaker` (dashboard recomputes nothing and resolves no day inline; same limit as the breaker for a normal row AND for a **dict-shaped** row, where the dashboard used to read 5R while the breaker rejected it to 3R; the endpoint reads the UTC day), `TestExchangeSyncLatch` (the latch threshold is not a hardcoded literal, the bound limit goes through the shared clamp, **the computed `limit_r` is the value that actually gets bound** — a hardcoded `{"limit_r": 3.0}` in the params passes every other test, so this is the load-bearing one, winning days are excluded by the positive limit rather than a floor — asserted by **`test_the_limit_is_always_positive_for_every_rejected_input`** (every rejected input still yields a positive limit) plus **`test_the_sync_expression_carries_no_floor_operator`** (no `GREATEST`, `COALESCE` present); the earlier version of the first test asserted `3.0 > 0` over a hardcoded tuple and never called the helper, so it stayed green through a rewrite returning 0 or -1), the comparison uses the breaker's own spelling, and the sync still sets absolute aggregates rather than accumulating), and `TestTheRulesExistInExactlyOnePlace` (the repo-wide guards: the clamp-shape duplicate check, its explicit positive case, and the `.today()` day guard). Source-contract checks are **AST call-shape**, not substring bans: a `date.today()` text ban sails past `datetime.now().date()` — the naive-tz equivalent — while a legitimate `datetime.now(timezone.utc)` TIMESTAMP must not trip them; the day guard is an AST walk for the same reason, since the docstrings this change added name `date.today()` in order to warn against it and a text ban would fail on the documentation of the fix. The runtime UTC-day ENDPOINT proof was REMOVED deliberately: pinning the process `TZ` east of UTC only forces `date.today()` off the UTC day while UTC's time-of-day is 21:00-24:00, so it failed for 21 hours of every 24. The property stays pinned structurally by `test_the_dashboard_resolves_no_trading_day_inline` and behaviourally by `TestTodayUtc::test_it_resolves_the_day_in_utc_and_returns_that_date`, which asserts the `tz` ARGUMENT against a frozen clock and so is valid at any wall-clock time. `TestExchangeSyncGroupsByTheUtcDay` / `TestExchangeSyncSourceContract` cover the recompute's UTC day key and date-based `:first_day` window (it used to group by session-LOCAL `DATE(closed_at)` and filter on a 48h TIMESTAMP, which truncated the boundary day); they evaluate the statement's REAL extracted expressions against Postgres over synthetic `VALUES` and assert the pinned session zone took effect, so they cannot pass on broken plumbing, and the UTC-key test includes a contrast assertion that the OLD expression does split the day. The `used_r` guard matches the formula as an **AST shape keyed on the negation**, not on any identifier: a two-argument `max()` whose first argument is the constant `0` and whose second is a unary negation must sit inside `used_r_from` and nowhere else. Both earlier versions of this guard are **known defects**, each of which went green over **zero** matches: (1) the literal substring `max(0.0, -float(` stopped existing the day the non-finite guard hoisted the `float()` into a local; (2) the AST rewrite kept the identifier assumption (`"total_pnl_r" in <args> or "total_r" in <args>`), which hoisting defeats identically — `ast.unparse` of the real call's args is `'0.0'` and `'-value'`, neither of which names the column. A hoisted local is the NORMAL state of `used_r_from`, so an identifier-based guard is guaranteed to miss. `test_the_guard_finds_the_real_clamp_it_exists_to_protect` now asserts the positive case explicitly (exactly one site, and it resolves to a `used_r_from` owner) because a guard matching zero sites is worse than no guard — it reads as coverage. Mutation-verified: an inline `max(0.0, -float(daily.total_pnl_r))` in `dashboard.py` and the **hoisted** form (`v = float(...); max(0.0, -v)`, the case the old guard missed) both turn it red. Shape matching also removes a latent false positive — `"total_r"` is a substring of `total_risk_distance`., and the day guard pins that no module under `backend/` makes a zero-arg `.today()` call. Every DB-touching case uses a private `NullPool` engine per phase (the shared pool is loop-bound) and purges in `finally` — `daily_summary` is the breaker's own input, so a leaked row moves the live allowance. Setting-row tests snapshot/restore rather than delete, and seed the BARE SCALAR shape `PUT /settings/trading` actually writes.

- **Tests MUST NOT leak rows into the database they run against.** The suite runs against `cfg.DATABASE_URL` (`localhost/fubot`), so a test that inserts without cleaning up permanently pollutes the dev database — and the Performance page reports it. Four `_close_position` tests (CLOSETST/TPHITTST/SWEEPTST/FLATTST) deleted `Order` and `Position` in their `finally` but not `Trade`; `_close_position` inserts one, so ~238 phantom rows accumulated over time and became most of the trades table. **Every test that calls a code path which writes a row must delete that row in `finally`** — check `session.add`, and for close paths that means `Trade`, not just `Position`/`Order`. Verify with: purge `WHERE symbol LIKE '%TST%'`, run the suite, and assert the count is unchanged (an idempotence check, since a per-file run can look clean while the full suite leaks). **A second instance of the same class was found 2026-10-17 and is the reason this check must be run against the FULL suite**: `test_services.py`'s `close_all_positions` test deleted `Position` but not the `Trade`, leaking one `CLOSEALLUSDT` row per full-suite run — 35 had piled up and inflated the local trades count from 48 to 80. Production was checked and had zero such rows.
