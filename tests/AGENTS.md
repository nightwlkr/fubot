- Run: `PYTHONPATH=. pytest tests/backend/ -q` using the system Python 3.13 pytest (`/Library/Frameworks/Python.framework/Versions/3.13/bin/pytest`)
- `conftest.py` puts the repo root on `sys.path` and provides a `db_session` fixture (rolled-back async session via `AsyncSessionLocal`). No custom `event_loop` fixture — pytest-asyncio 0.24 deprecates it, and a session-scoped loop coupled every async test to one loop.
- `test_api_smoke.py` uses a FUNCTION-scoped client (fresh app lifespan per test) so the engine's DB session never spans TestClient portal lifecycles; its `_run` helper restores the thread's current event loop after `asyncio.run` (asyncio.run leaves `set_event_loop(None)`, which breaks the next async test under pytest-randomly)
- **Tests MUST NOT leak rows into the database they run against.** The suite runs against `cfg.DATABASE_URL` (`localhost/fubot`), so a test that inserts without cleaning up permanently pollutes the dev database — and the Performance page reports it. Four `_close_position` tests (CLOSETST/TPHITTST/SWEEPTST/FLATTST) deleted `Order` and `Position` in their `finally` but not `Trade`; `_close_position` inserts one, so ~238 phantom rows accumulated over time and became most of the trades table. **Every test that calls a code path which writes a row must delete that row in `finally`** — check `session.add`, and for close paths that means `Trade`, not just `Position`/`Order`. Verify with: purge `WHERE symbol LIKE '%TST%'`, run the suite, and assert the count is unchanged (an idempotence check, since a per-file run can look clean while the full suite leaks). **A second instance of the same class was found 2026-10-17 and is the reason this check must be run against the FULL suite**: `test_services.py`'s `close_all_positions` test deleted `Position` but not the `Trade`, leaking one `CLOSEALLUSDT` row per full-suite run — 35 had piled up and inflated the local trades count from 48 to 80. Production was checked and had zero such rows.
- Known-defect tests use `@pytest.mark.xfail(strict=True)` with a precise reason — when the defect is fixed, the strict xfail fails the suite and forces the marker's removal
